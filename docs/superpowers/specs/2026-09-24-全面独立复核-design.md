# 全面独立复核：方案设计

## 任务性质

这不是新功能开发，而是对既有程序的独立复核 + 确认问题修复 + 文档同步。因此"方案"比较的是复核与修复的组织方式。

## 方案比较

| 方案 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| A. 逐文件静态阅读 + 全量测试 + 针对性探针（推荐） | 逐文件通读全部源码，跑现有 pytest 全量与回归基线，对可疑点写一次性探针脚本实测；确认的 bug 按 TDD 修复 | 时间最长 | 低，证据链完整 |
| B. 只跑测试 + 抽查重点文件 | 依赖现有测试覆盖，抽查 group_processor 等核心 | 快 | 现有测试未覆盖的模块（gui/app、make_excel、reader 部分分支）漏检 |
| C. 静态分析工具扫描 | 跑 pylint/bandit 之类 | 快 | 产生大量噪音告警，业务正确性问题查不出 |

推荐 A：复核的价值在"结果悄悄出错"类隐患，只有通读 + 实测能覆盖；B、C 可作为 A 的组成部分而非替代。

## 复核维度（每个文件逐项过）

1. 数据完整性：金额是否守恒、行是否不重不漏、红字/空科目/零金额/借贷双非零的走向。
2. 逻辑正确性：算法边界、分组键、排序恢复、异常分支。
3. 与 README 的一致性：功能描述、参数、输出结构、算法原理章节。
4. 测试质量：是否验证行为而非 mock；正常/边界/错误路径是否齐全。
5. 过度工程与死代码。

## 修复策略

- 每个确认的 bug：先写失败测试（放 `tests/`，跟随现有中文命名风格），再最小修复，再跑该测试 + 全量 pytest + 回归检查。
- 无法实证的疑点只写入复核报告，不改代码。
- README 修正集中在最后统一改，改前备份。

## 数据流与错误处理

本次复核不改变程序数据流。验证手段：
- `python -m pytest tests/ -x -q`（GUI 测试依赖本机桌面环境）
- `tests/regression_check.py` 的捕获/验证（如需）
- 一次性探针脚本放系统临时目录，不进仓库。
